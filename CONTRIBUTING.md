# Contributing

## Workflow

Read `AGENTS.md`, `CONTEXT.md`, the relevant ADR, and `docs/openapi.yaml` before a change. Implement one testable slice, run its checks, and present the commit suggestion required by `AGENTS.md`. Never stage or commit without explicit user approval.

## Commit Messages

Use Conventional Commits:

```text
type(scope): concise imperative summary
```

Examples:

```text
feat(characters): add cached catalog endpoint
fix(cache): preserve stale catalog data on timeout
test(api): cover invalid pagination input
docs(agents): document incremental handoff protocol
```

Keep each commit narrowly scoped, independently reviewable, and supported by applicable tests. Do not combine a feature with opportunistic refactoring or broad formatting.

The header must include one of the types and scopes defined in `AGENTS.md`, stay within 72 characters, and describe the verified intention in concise imperative English. For `frontend`, name the affected feature in the subject. Intentional breaking changes require both `!` and a `BREAKING CHANGE:` footer. Review precision and factual accuracy manually; passing syntax checks does not authorize a commit.

## Local Commit Validation

With Node 22.12+ and the pinned pnpm version, run `pnpm install --frozen-lockfile`. The `prepare` script installs Husky's local `commit-msg` hook; use `pnpm run prepare` to restore it after an install with scripts disabled. The hook invokes the installed commitlint CLI, without staging, formatting or committing files. Merge/revert messages generated by Git retain commitlint's standard exceptions.

Use `pnpm run lint:commit` to validate a message from standard input and `pnpm run test:commits` to check accepted/rejected examples and the installed hook without creating a commit. `commitlint.config.mjs` is the executable convention. Node must be available to the Git client, including when committing from a GUI.
